# AI usage monitoring

`get_usage(days)` remains unchanged. The read-only `get_ai_usage()` tool reports Farm-observed `usage_events` where `kind='actual'`, summed separately per account and unit for the tenant's calendar day and month. Calendar boundaries use `farm_settings.timezone` (IANA; invalid values fall back to UTC). Units are never combined, and reservation estimates are not included. Positive `cost_usd` event totals are shown as known Farm-metered cost. Zero-cost events are counted separately as zero-or-unknown because the event schema cannot distinguish free use from a missing price. These amounts are not subscription billing totals. Failed/cancelled AI jobs without a matching actual usage event are counted as missing metering rather than zero usage.

Provider allowances are a separate section. A Codex check uses the documented app-server JSON-RPC handshake (`initialize`, `initialized`) and the read methods `account/rateLimits/read` and `account/usage/read`. It retains allowlisted numeric rate windows and daily token buckets only. Per-account `home`/`config_dir` isolation is required; `cli_prefix` is honored for accounts launched through a shim. No credential files are read directly. Codex CLI must be installed and available to that configured launcher.

Claude, Gemini CLI, and Antigravity expose no supported headless provider allowance interface here. They return explicit `unsupported` allowance status; Farm-local daily/monthly event totals still work. Claude's documented `rate_limits` status-line data is interactive-session-only and is not queried.

The scheduler polls due active AI accounts serially in batches of at most 32 (default four), with a configurable tenant interval in `ai_usage_settings` (default 600 seconds). Usage polling runs in its own scheduler task with a 60 second total tick bound. Routine `run_maintenance_tick` calls do not probe unless `include_usage=True`. Queued/running accounts and paused, disabled, exhausted, or `needs_login` accounts are skipped; an account with running work can be monitored after three poll intervals from the job's `started_at` (or `created_at` when not started), including when no prior allowance snapshot exists. Disabled providers are skipped too. A transaction-level database advisory lock keyed from the trusted tenant context remains held for the full probe batch and releases automatically on completion or cancellation. Failures update check status while retaining the last successful snapshot and observation time. Any failed latest check makes allowance freshness stale; missing observations and future observations are unknown, and old provider windows are stale. Probe errors do not update account health, availability, or exhaustion. Each subprocess is capped at 15 seconds; stdout and stderr have independent 256 KiB caps, and process trees are killed on timeout.

The report includes every AI account, including accounts with no observed events. Accounts without a provider snapshot have allowance status and freshness `unknown`, with a null snapshot. `account_call_counts` reports per-account distinct non-null `request_id` counts as a lower bound plus counts of actual events with null request ids. Multiple unit events for one request count as one call. Rows in `observed_usage` retain compatible per-unit call fields, so those account-level values repeat across units and must not be summed across units. Call status is `partial` when any event lacks a request id, `observed` when identified calls exist without unidentified events, and `unknown` otherwise. Event counts and amounts include only `actual` events in the tenant calendar windows and are bounded by report time, so future-dated events are excluded. Reported event costs are known only where Farm received a positive cost; zero-cost events remain zero-or-unknown because this schema cannot distinguish free use from missing price. Failed or cancelled jobs without a matching actual event are counted globally and on each account row as `day_jobs_without_metered_events` and `month_jobs_without_metered_events`. These are job-only counts, not usage events or per-attempt attribution; per-attempt metering cannot be reconstructed when only job-level run ids are present. Provider-reported quota values remain absent when unsupported rather than appearing as zero.
