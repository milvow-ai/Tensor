## Architecture implications
**Recommended stack.** One Postgres 18 (official Docker image, named volume) holds domain data and workflow state; the same Compose file runs on the VPS. DBOS Transact runs inside api and worker processes: workflow ID = CapabilityRequest hash gives single-flight, queues give concurrency, rate limit, priority and dedup, schedules live in the database. DBOS steps are at-least-once, so provider calls go ledger-first: reserve units, call, settle. A request_ledger table (UNIQUE request_hash, expires_at) is the response cache; no Redis. Put DBOS behind a WorkflowPort; the pipeline interpreter takes a frozen JSON snapshot as input. Alembic migrations; pg_dump nightly to R2, pgBackRest on the VPS. BlobStore port: local files with sha256 keys, then R2 or Garage, never MinIO. structlog plus OpenTelemetry (DBOS spans) to a Phoenix container; Sentry free for errors. sops+age secrets. tldextract (private suffixes on) plus pg_trgm for entity keys; Splink later. Supabase and Neon Free lose: pausing, 500 MB, no backups, and always-on polling would exhaust Neon compute in about 17 days [mine].

**Strongest alternative: Hatchet.** It lost because it adds a second stateful service (Go engine; Lite is documented for development and low volume), while DBOS is a library in our own Postgres. Hatchet wins if we need a bundled dashboard, per-key dynamic rate limits or CEL concurrency keys; switching costs one adapter.

**DBOS lock-in: moderate.** MIT and plain tables, but young (repo created 2024-07-19), fast-moving (pin versions), and multi-worker crash recovery needs proprietary Conductor or self-managed executor IDs.
