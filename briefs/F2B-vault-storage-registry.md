# F2B — Encrypted vault per tenant, file storage, and per-tenant registry

Rules for every step: touch only the files under **Owns**. Never run `git add / commit / push / reset / checkout / stash`, deploy,
delete anything outside this worktree, or send data off this machine. Never read or print any `.env` file or secret value — tests
use generated test keys only. Never run a migration against a live database. Run every command in the foreground; run ruff, mypy
and the relevant test files yourself (the gate runs the full suite after you).

**Goal.** Each tenant must bring its own keys and logins without them ever sitting in one `.env`, and files produced by agents need
a home that works the same on one PC and on many servers. `docs/ARCHITECTURE.md` §7, §13, ADR 8, 21.

**Read first:** `briefs/CONTEXT.md` (§2 secrets rules) · `docs/ARCHITECTURE.md` §7, §9, §13 · `farm/secrets.py` (`resolve_auth`,
`redact`) · `farm/registry/{loader,sync,writer,models}.py` · `farm/executors/mcp/connect.py` (OAuth token store) ·
`farm/db/pool.py` (F1B checkouts).

**Build:**
1. **VaultPort + envelope encryption** — `farm/vault/`: a master key from `FARM_MASTER_KEY` (32 bytes, base64; generated by a new
   `farm vault init` command that prints instructions to add it to `.env` and never prints the key twice); per-tenant data keys
   (AES-256-GCM via `cryptography`) stored wrapped in `tenant_keys(tenant_id, version, wrapped_key, created_at)`; secrets in
   `vault_secrets(tenant_id, name, version, nonce, ciphertext, created_at, created_by)`. API: `put(name, value)`, `get(name)`,
   `rotate_tenant_key()`, `delete(name)`; values are `SecretStr` everywhere and never logged, returned by a tool, or stored in plain text.
2. **`vault:` auth refs** — `resolve_auth("vault:<name>")` reads the current tenant's secret (tenant from the F1B context). Existing
   `env:` / `token-store:` / `cli:` refs keep working for tenant #1.
3. **OAuth token store per tenant** — the MCP OAuth token store (today a file store) can live in the vault (one secret per
   connection), behind the same interface, so tokens follow the tenant to any server. Keep the file store as the local-dev option.
4. **StoragePort** — `farm/storage/`: `LocalDiskStorage` (dev, under `FARM_DATA_DIR/objects`) and `S3Storage` (any S3-compatible
   endpoint via `boto3`/`aioboto3`, configured by env names only); keys `t/<tenant_id>/<area>/<id>`; `put`, `get`, `delete`,
   `signed_url(ttl)` (local dev: a short-lived token URL served by the api role later — return a placeholder `file://` path now),
   per-tenant byte quota check. Tests run against `LocalDiskStorage` and a moto (or MinIO-like) S3 fake — no real cloud calls.
5. **Registry per tenant** — `farm registry sync --tenant <slug>` writes providers / connections / capabilities / routes / budgets for
   that tenant only; the database is the runtime source of truth; YAML is import / export per tenant.

**Tests:** encrypt/decrypt round trip; tenant B cannot read tenant A's secret even with its name (RLS + key separation);
a wrong master key fails closed; secrets never appear in logs (capture logs in the test); key rotation re-wraps without losing
secrets; storage keys are tenant-prefixed and a tenant cannot read another tenant's key; registry sync for tenant B leaves A untouched.

**Database changes:** one migration `farm/db/migrations/versions/0021_f2b_vault_storage.py`, `down_revision = "0020"` (F2A; if F2A is
not merged when you start, chain to the latest revision and say so), full downgrade.

**Dependencies:** `uv add cryptography` (if not present) and `uv add --dev moto[s3]`; `uv add aioboto3` only if you use it.
